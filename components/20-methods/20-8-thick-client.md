# 20.8 · Thick Client Penetration-Testing Method

> Framework component for adaptation. Publication does not authorize testing, certify conformance, or establish that an organization has adopted this practice.

## What a thick-client test is actually testing

A "thick client" here is any installed desktop or workstation application that performs meaningful work on the endpoint itself — in contrast to a browser tab or a thin client that mostly renders server-side state. The defining property is that **code and often data sit on a machine the user (and a local attacker, or a co-tenant on a shared host) can inspect, instrument, and modify.** That single fact reshapes the threat model: the binary, its local storage, its inter-process surface, and the channel it opens to a back end are all reachable from the endpoint, and the endpoint is not a trusted vantage point.

A thick-client assessment asks a bounded question for each tested path: *can a defined actor — a low-privilege local user, a user who can read and modify the client, or a position on the network the client talks across — reach, read, forge, or cross a control the application depends on, and what does the captured evidence actually prove about that control?* The aim is a defensible account of the **tested path**, not an inventory of every decompiled string with an endpoint-wide story attached.

Use this method with the umbrella penetration-testing method (§20.1), the scope / rules-of-engagement / requirements records (§10.1 / §10.2 / §10.4), the adopter's own evidence, safety, and reporting rules, and the handling rules for whatever sensitive data the client touches. It covers the compiled or packaged client across common framework classes, its data at rest and in memory, its inter-process and local-privilege surface, its embedded-web and automation surfaces, its update channel, and the client↔back-end transport. Deep back-end work hands off: server-side API behavior to §20.3, direct-database behavior to §20.7, embedded web content to §20.2, host/directory privilege beyond the client's reach to §20.6, and embedded-LLM/agent behavior to the AI/LLM method. Discovering one of those surfaces through the client does **not** add it to the authorization.

### Scope boundaries worth stating explicitly

- **In:** native compiled desktop apps; managed-runtime apps (e.g. .NET, Java); web-runtime desktop wrappers (e.g. Electron and other Chromium wrappers, system-WebView wrappers); cross-platform UI toolkits; and the same applications on macOS and Linux where present. The update mechanism, the inter-process surface, and any local-privilege path reachable **from the client's process boundary** are in scope when the engagement says so.
- **Out (route elsewhere):** mobile apps; pure in-browser web applications; embedded firmware / IoT; operating-system vulnerabilities not reachable from the client; network and directory infrastructure not reachable from the client. An installed "progressive web app," an embedded browser engine inside the client, and an embedded AI/automation integration are all **in scope as components of the thick client** when the engagement names them — call that out at scoping rather than discovering it mid-test.

A thick client is frequently a façade over surfaces that have their own methods. Testing the client well means knowing when you have reached the edge of the client and are now looking at an API, a database, a web app, or a host — and handing that off under its own authorization.

## Identify the framework class early — it changes the route

An early decision in a thick-client test is **framework classification.** The toolchain, the reachable attack surface, the reversing workflow, and even whether "decompilation" is a meaningful step can differ sharply between a native compiled binary, a managed-runtime assembly, a Chromium wrapper that ships much of its logic as script, and a system-WebView wrapper. Misclassification can waste the test window and distort the coverage claim.

Classify at triage, from observable signals, and record **how** the class was determined (a confirmed signal, or an inference to be confirmed):

| Framework class | Illustrative identification signal | What the class changes |
|---|---|---|
| Native compiled (C / C++ / Rust / Go) | No managed-runtime header; packer/format detector identifies a native image | Disassembly/decompilation and native debugging; compiler-mitigation posture is a real surface |
| Managed runtime (.NET family) | Managed-runtime header present; assemblies open cleanly in a decompiler | Decompile/patch the intermediate representation; runtime diagnostics via the platform's own tooling; ahead-of-time/trimmed builds fall back to native workflow |
| Managed runtime (Java family) | Spawns a JVM; archives and class files enumerable | Decompile to source; check for an exposed debug-wire protocol; JVM instrumentation |
| Chromium/Node wrapper (Electron-class) | Packaged app archive and a vendored Chromium/Node runtime | Ships as readable script; the integrity fuses, renderer preferences, and the renderer↔host bridge are the dominant surface |
| System-WebView wrapper | Spawns the OS WebView process at runtime | The host-object bridge between embedded web and host code is the dominant surface |
| Minimal-runtime WebView wrapper (Tauri-class) | Small native core plus the system WebView; capability manifest in the app directory | A declared capability/allow-list model gates what the web layer can reach; audit the manifest and each native command handler |
| Cross-platform UI toolkit (Qt-class, Flutter-class) | Toolkit libraries imported; ahead-of-time-compiled UI layers | Reversing difficulty varies; often more productive to focus on traffic and inter-process surface than on binary reversing |
| macOS-native (Cocoa/Swift) | Mach-O image; signature and entitlements present | Entitlements, the platform consent model, and privileged helper services are the distinctive surface |

Treat the table as a routing aid, not a checklist. The class tells you where the surface concentrates; the rest of the method is about proving what is actually there.

## Fix the path, the trust boundaries, and the stopping point before acting

Before any instrumentation or modification, the engagement record should answer each decision below. These can live in an existing intake, rules-of-engagement document, or brief — this is not a mandate for a new system.

| Decision | Record that makes the test bounded |
|---|---|
| Authority and actor | Owner; authorized application, version(s) and modules (and out-of-scope versions/modules); the actor model under test (low-privilege local user, user-who-can-modify-the-client, specific network position); permitted test classes; test window; escalation and stop contacts. A tool approval or endpoint access does not enlarge this. |
| Trust-boundary model | Is the architecture 2-tier (client talks to a data store directly) or 3-tier (client → application service → store)? Where are the local trust boundaries: the client's own process boundary, its inter-process endpoints, any privileged helper/updater, and any embedded-web↔host bridge? Who can confirm the *intended* boundary? |
| Explicit scope switches | Is the **update mechanism** in scope (it can pull live versions during the window)? The **embedded browser engine**? **Inter-process / automation integration** (including any embedded AI/agent)? **Local privilege escalation** reachable from the client? **Red-team / defense-evasion** technique (usually excluded — state it)? **Dependency / supply-chain** review (often a parallel workstream)? |
| Safety and isolation | Use an **approved, isolated test rig** suited to the client and data. A managed test device may be appropriate when its owner explicitly permits the install, instrumentation, monitoring and restoration path; a production-user endpoint is not a convenient default. Record a recoverable baseline before testing. Keep modified/instrumented binaries under custody and remove them at close. Coordinate with defenders before modifying live traffic. |
| Data and evidence | Use synthetic or approved accounts; never use production credentials unless explicitly authorized and scoped. Collect sensitive data only to the degree a finding requires; protect originals; redact recipient copies; define retention and cleanup. Never upload captured secrets, decompiled source, or traffic to an unapproved service. |
| Coverage limit | What is unavailable or deferred: a framework class the rig can't run, a module out of window, an unissued credential, a protected update feed that can't be exercised, a surface excluded by the rules. A limited vantage point limits the conclusion. |

Rig readiness (the isolated workstation, the onboarding baseline, a managed rig) is addressed by the adopter's workstation and onboarding standards (e.g. §40.1 / §40.3 / §40.10); rig readiness is **not** engagement authority. Credential handling follows the adopter's credential-handling rule (e.g. §30.3).

The tester first establishes a known-good baseline: launch the client in a clean snapshot, capture its normal file, registry/preference, inter-process, and network behavior, and confirm the actor identity actually in effect. A baseline capture is what later lets an observation be read as a *change* rather than as normal behavior.

## Build a surface map from the running client, not from a tool's default output

For the in-scope client, inventory what it actually does and where it keeps and sends state:

- **Function and privileged operations:** map observable features; flag anything that imports/exports configuration, handles credentials, touches the file system broadly, opens listeners or inter-process endpoints, spawns child processes, or invokes an updater or helper.
- **Architecture:** investigate whether the client reaches a data store directly, uses an application service, or mixes paths. Observed traffic is evidence for the path exercised, not proof of the entire deployment architecture. A direct-store client may hold or obtain reusable access material, but determine the actual identity, store authorization, network and broker controls rather than assuming the store is its only enforcement point. If a nominally service-mediated client also reaches the store directly, confirm intended design and impact before treating that path as a finding.
- **Local footprint:** every file, preference/registry location, and inter-process endpoint the client reads or writes during normal use; the embedded-web↔host bridge if present; the updater and any privileged helper.
- **Network:** every inbound/outbound connection during normal use, with baseline captures to diff later; the transport and protocol (HTTP(S), a database wire protocol, gRPC, WebSocket, a custom binary protocol, a local socket or pipe).

Mark each surface **observed**, **documented-but-untested**, **in-scope-but-unreachable**, **excluded**, or **ownership-unknown** — separately. Record where a version, protocol, or key is **inferred** rather than verified. A surface map is a precondition for an honest coverage statement; a scanner's or decompiler's default dump is not one.

## Select the test families that fit that map

The families below are the thick-client manual testing surface. Each is a bounded question with the kind of evidence that would actually change the answer. Treat the control/weakness/technique vocabulary (a thick-client control standard such as OWASP TASVS; a weakness taxonomy such as CWE; an adversary-behavior catalog such as MITRE ATT&CK) as a **mapping aid for reporting**, verified against its current primary edition at engagement time — not as a severity oracle and not as proof that a mapped behavior occurred.

| Family | Bounded question | Evidence that changes the answer |
|---|---|---|
| Transport & interception | Is sensitive traffic protected in transit, and does the client validate the server it talks to? | Captured transit content and the client's actual certificate-validation behavior. A proxy that succeeds only after a deliberate trust-store or pinning change must say so; "I MITM'd it after installing my own CA" is a different claim from "the client accepts any certificate." |
| Signing & binary-protection posture | Is the shipped binary signed/notarized as expected, and are platform compiler mitigations present? | The actual signature/notarization state and mitigation flags on the real image. A missing control is a hardening observation that may become a finding against the expected baseline; it is not by itself a demonstrated compromise. |
| Insecure data at rest | What does the client persist (files, preferences/registry, platform keystore, app-managed encrypted stores), and is sensitive data protected? | The actual stored content and its protection: cleartext secrets/sensitive data, over-broad scope on platform-protected storage, app-managed crypto with a recoverable key or reused IV or missing integrity, world-readable or world-writable locations. A world-writable high-privilege config is also a local-privilege path (below). |
| Authentication & session | Does authentication actually hold against a client the user can modify, and are sessions and tokens handled safely? | Whether a modified client can access a protected operation without a valid server-side authorization decision (distinguish intended offline functions); desktop OAuth/OIDC behavior (is the proof-key used where the flow requires it; is the redirect target validated; what abuse path, if any, does a device-code flow expose?); token storage and rotation; whether a session timeout terminates the relevant access and clears sensitive state; whether a "biometric succeeded" assertion is independently validated where required. |
| Authorization & privilege boundaries | When the UI hides a privileged feature, does the **server** still enforce it? | A low-privilege actor invoking a privileged operation directly (replayed call, direct endpoint, object-reference change) and the server's response; or unlocking the hidden UI in the client and observing whether the privileged action is actually honored. Client-side-only authorization is an important class, but the claim is earned by showing the back end does not enforce, not by showing the UI changed. |
| Injection surfaces | Does user- or externally-controlled input reach an interpreter, a shell/helper invocation, a file-path operation, embedded web content, or an embedded LLM without adequate neutralization? | Input traced to the sink with its effect: a data-store query in a 2-tier client, a command/argument reaching process creation, a traversal reaching a sensitive path (higher impact when the client runs elevated), injected markup in an embedded web surface that can reach a privileged bridge, or an injected instruction an embedded LLM acts on. A payload that is reflected is not yet a payload that executed. |
| Local privilege escalation | Can a low-privilege local actor use the client (or its helper/service/updater) to run or write as a higher-privilege identity? | A concrete, permissioned path: a search-path/library-load location that is user-writable while the client runs elevated; an unquoted or misconfigured service path; a hijackable component registration; a check-time/use-time race against a privileged helper consuming a user-controlled path; a symlink/junction swap on a path the client writes. Document the **exact path and its permissions** — defensibility depends on the permission scope, not the theory. |
| Inter-process surface | What local endpoints does the client expose, and can a lower-privileged caller reach a privileged action through one? | Each endpoint (named pipe, platform object model, platform XPC/Mach or local socket, desktop-bus service, embedded-web host bridge) with its access control, whether a low-privilege caller can open it, and what a message across it can cause. An unauthenticated local control endpoint on a privileged helper is a privilege path. |
| Reverse engineering & logic recovery | What does the absence of reverse-engineering resistance expose, and can client-side protected logic be recovered? | Recovered authentication/crypto/network logic sufficient to explain a finding; a reproduced decryptor for an app-managed store built from the client's own (recovered) key and algorithm. Reversing is both a technique and a test of the RE-resistance control — testing it confirms and exploits the absence of protection, but the *finding* is the exposed secret or logic, not the act of decompiling. |
| Memory exposure | Does the live process hold sensitive data in cleartext beyond its useful life? | Strings/structured content scraped from the running process or a dump: connection strings, tokens, cleartext sensitive data, credentials not zeroed after use or retained across a session timeout. Memory is the attack surface for an actor with debugger-level access even when the on-disk copy is encrypted. |
| Logging & side channels | Does the client leak sensitive data to logs, crash reporters, the clipboard, on-screen debug surfaces, or temp files — and are its own audit events trustworthy? | The actual content of logs/temp files/telemetry, their access controls and retention, and whether audit events exist for sensitive operations. A log containing credentials or sensitive records may establish an exposure even when transit is protected; assess who can read it and the intended logging policy. |

### Modern framework-specific surfaces

These framework-specific classes can change where the relevant trust boundary sits. Select a branch only when the client actually exposes it.

- **Chromium/Node wrappers (Electron-class).** A packaged archive may expose readable script, making source-level review possible. Examine runtime behavior controls, renderer configuration (context isolation, sandbox, origin boundaries), renderer↔host bridge functions, deep-link handlers and update integrity. Each setting is a lead until the expected baseline and a reachable effect are established. A renderer injection that reaches a privileged host function, or a deep link that executes a controlled command, is a chain only when each link is demonstrated under authority. Verify any version-specific advisory from its primary source at engagement time.
- **System-WebView wrappers.** The host-object bridge is the dominant surface; audit each exposed host object exactly like the Electron bridge. Cookie/SSO material rendered in an embedded sign-in surface can be read by the embedding host — relevant when a trojaned client could be substituted for the legitimate one (a supply-chain precondition, which should be stated, not assumed).
- **macOS-native clients.** The distinctive surface is the platform consent model (does the app request only the access its purpose justifies; are there consent-bypassing entitlements), the entitlements and hardened-runtime posture, and privileged **helper / XPC** services — the dominant macOS local-privilege class is a privileged helper that fails to validate the calling code's signature or consumes a user-controlled path (a check-time/use-time race). Patching a Mach-O requires re-signing to run; note that as a workflow constraint.
- **Minimal-runtime WebView wrappers (Tauri-class).** Audit the declared **capability/allow-list** manifest (what the web layer may reach) and each native command handler the web layer can invoke.
- **Other cross-platform toolkits.** Java-class clients: check for an exposed debug-wire protocol (a remote-code path) and classic deserialization exposure, decompile for logic. Ahead-of-time-compiled toolkits (Flutter-class, trimmed/AOT managed builds): reversing is costly — it is often more productive to concentrate on traffic and inter-process surface.
- **Update channel.** An updater may reach the network, write protected paths, or run with elevated privilege. Establish its actual identity and permissions. Audit feed authenticity, artifact integrity, and any privileged helper that applies an update. A weak transport or absent signature is a precondition to assess, not proof of executable replacement. Exercise the path only against a controlled feed within explicit scope.
- **Dependency / build-pipeline surface.** The client is the output of a build. Dependency review and build-pipeline trust are often a parallel workstream. A dependency named in a manifest is a lead: verify the affected build, reachability, exploit conditions and scope before stating consequence. Artifact-signing and build-secret controls are questions for the appropriate owner, not findings presumed from the client alone.
- **Embedded AI / agent integration.** When a client embeds an LLM or an agent/tool integration, the tool surface and the model's untrusted-input intake (clipboard, screen content, files, network responses) are attack surface: a tool-description or tool-registration poisoning path, and prompt injection via any content the model consumes. Route the model-behavior depth to the AI/LLM method; here, treat the integration as inter-process + input surface and bound every claim by whether the agent *actually acted*.
- **Defense-evasion / red-team technique.** Usually **out of scope** for a thick-client assessment; confirm explicitly. Where in scope, it is governed as scope discipline — agree which techniques are permitted, the defender-notification posture, and the detonation cadence; document every technique used and preserve indicators for the defenders' retrospective. This method does not carry an evasion how-to.

## From primitive to demonstrated impact — the evidence ladder

A reachable surface is not a broken control, a missing mitigation is not a demonstrated compromise, a decompiled secret is not a used credential, and a tool's output is not a finding. Hold every candidate to three evidence states:

1. **Observed or demonstrated.** The authorized actor, from the authorized position, produced an actual result — a captured response, a read control posture, a recovered secret, a reproduced decryption, or a message accepted across an endpoint. State whether that result merely shows a condition or demonstrates a prohibited effect. Preserve the exact client version and state, actor and privilege, action, result, and limits.
2. **Supported inference.** The observed posture makes a follow-on path plausible under stated preconditions. Name the missing step and the alternative explanations. A missing mitigation flag suggests exploitability but does not establish a working exploit; a client-side role flag that flips does not establish that the server honors the privileged action; an exposed update feed does not establish a delivered update.
3. **Not tested.** The next step would require a credential, another host, a different method, a disruptive or impact-bearing action, or data access not authorized here. Route it to the owner as a next question — do **not** write the imagined final step as fact.

**Worked, synthetic example.** On an isolated rig, the tester opens a running managed-runtime client in a process inspector and finds, in memory, a database connection string with an embedded credential. That is **observed**: the string was present in cleartext in the live process. It becomes a **supported inference** that the client is 2-tier and that the credential would reach the store directly — *if* the architecture is confirmed and the credential is in scope. Connecting to that store and reading records is a **not-tested** step until the engagement authorizes direct-store access against an approved target; if authorized and performed against the approved synthetic store, it returns to **observed**, and the report can say the tester reached that store under those conditions. It cannot say "the production database is compromised," that every deployment behaves this way, or that the reachable data is sensitive and in scope unless each of those was separately established.

Severity follows the **observed condition, credible impact, exploit preconditions, exposure, and the adopter's scoring model and business context** — never a fixed number attached to a primitive. A higher potential impact can be stated as conditional when it has not been demonstrated. A control-mapping or adversary-technique label describes a category; it is not a rating and not a proof.

### Attack-chain families are hypotheses, not prewritten findings

Thick-client work recognizes recurring chains — each a *combination* of primitives that, when every link is earned through the ladder above, can carry real impact. Common families include:

- connection-string recovery → direct data-store access (2-tier);
- library/search-order hijack from a user-writable path → execution as the elevated client;
- update-feed poisoning (unauthenticated or unverified channel) → code execution as the updater;
- embedded-web injection → privileged host bridge → host code execution;
- custom-scheme / deep-link handler → one-click code execution;
- privileged local helper / XPC with weak caller validation → privilege escalation;
- desktop OAuth flow misuse → token exposure, when the actual client flow and preconditions support it;
- transport-validation bypass → interception → credential/sensitive-data capture;
- embedded-agent tool/description poisoning → agent goal hijack.

Each family is a question to test, with a remediation direction for the application owner: server-side authorization appropriate to the architecture; protected storage; authenticated update artifacts; a constrained renderer and validated bridge; handler input validation; caller and path validation on privileged helpers; controls appropriate to the actual authentication flow; certificate validation (and pinning where justified by the threat model); and validated tool registration. A named chain never grants scope and never, by itself, proves compromise.

## Handoff, report, and close

A useful finding packet contains: the expected control and the client version/state and actor it was tested against; the authorized procedure and the known-good baseline; authentic, protected evidence (with a redacted recipient copy); the observed effect with its uncertainty; a **bounded** impact statement; a specific, actionable remediation direction (not "use secure coding"); the control/weakness/technique mapping where it applies, with any regulatory mapping added **only** after scope and evidence are checked and only for the applicable requirement; a reviewer disposition (accept / reject / merge / split / defer-for-evidence / inconclusive, with the reason preserved); and a retest condition. Keep observed fact, inference, limitation, and recommendation visibly distinct, and state plainly what the test did **not** establish — a negative result is bounded evidence about the conditions tested, not proof the client has no weakness.

Hand off what belongs elsewhere under its own authorization: server-side API behavior (§20.3), direct-database behavior (§20.7), embedded web content (§20.2), host/directory privilege beyond the client (§20.6), network behavior (§20.5), and embedded-model behavior (the AI/LLM method). Those are method handoffs, not automatic scope grants. At close, reconcile temporary accounts, captured secrets, instrumented and modified binaries, rig snapshots, and any approved changes; **verify** restoration or owner acceptance rather than assuming cleanup because the window ended.

A second reviewer should be able to trace any accepted conclusion backward to the requests/actions, the client version and state, the actor identity, and the authorization — and to see where the tester stopped and why.

## Automation as a bounded, optional lane

Parts of this method can benefit from assisted triage — framework classification, signing and mitigation posture, suspicious patterns, renderer configuration, timed behavior monitoring, and mapping a human-authored finding to a current control taxonomy. Any such lane carries the same authorized-target and isolation boundary, custody of sensitive material, stop route, preserved provenance, and **human authority over every accepted finding and impact-bearing decision.** Assisted tooling proposes and triages; it does not confirm. This method does not imply that an agentic testing capability has been deployed or validated.

The output of this method is a reviewable account of what one authorized actor could and could not establish about one installed application. It is neither a certification nor a claim that any particular client passed every family above.
