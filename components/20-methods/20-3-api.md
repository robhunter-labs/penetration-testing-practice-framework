# 20.3 · API Penetration-Testing Method

> Framework component for adaptation. Publication does not authorize testing, certify conformance, or establish that an organization has adopted this practice.

## Purpose and fit

An API is a set of callable operations and data exchanges, not merely a list of URLs. The useful question is whether each caller can perform only the operations and see only the data intended for that caller, while the service remains bounded under abnormal input and load. This method helps a tester turn that question into a scoped plan, observations, evidence, and a defensible conclusion.

Use with the umbrella method (§20.1) and the local engagement authorization, rules of engagement, evidence handling, and reporting requirements. This guide covers REST, SOAP, GraphQL, gRPC, and API-backed browser or mobile flows when they are in scope. Web UI, mobile binary, infrastructure, database, and AI-specific behavior need their own methods; the API boundary can still be examined where the approved scope includes it.

The [OWASP API Security Top 10 (2023)](https://api-security.owasp.org/editions/2023/en/0x00-header/) is a risk-awareness map, not a complete test checklist or a severity calculator. The categories below guide coverage; the target's architecture and business flows determine the actual test design. Use the current OWASP edition at the time of an engagement and record which edition was used.

## Before a request is sent

The engagement record should answer these questions in plain language:

| Decision | Minimum useful answer |
|---|---|
| Authority | Who authorized testing, for which environments, hosts, operations, data, dates, and identities? Who can pause or stop it? |
| Boundaries | Which third-party, tenant, production, shared-service, administrative, and destructive actions are excluded or require separate approval? |
| Target model | What are the API versions and protocols, gateway and backing services, authentication flows, resource types, sensitive business actions, and expected caller roles? |
| Test identities | Which test accounts and objects belong to each role and tenant? How are credentials received, stored, rotated, and retired? |
| Safety | What request-rate, concurrency, data-volume, state-change, and notification limits apply? What is the agreed escalation path for unexpected impact? |
| Evidence | Where will request/response records, timestamps, target state, redactions, review notes, and report decisions be held with access control? |

An OpenAPI file, Postman collection, WSDL, GraphQL schema, or `.proto` file can accelerate inventory, but none proves the deployed surface is complete. If a required identity, permission, or safety boundary is missing, record the gap and resolve it before that branch of testing. Do not treat inability to test as a secure result.

## Establish a repeatable test position

Choose an API client and an intercepting/recording path that work for the protocol and engagement constraints. Product choice is not the method. Verify a benign request reaches the intended environment, authenticates as the expected identity, yields the expected response, and produces a usable evidence record. If TLS interception is used, apply a test-only trust configuration under the engagement's device and credential policy; remove it afterward. Do not weaken certificate validation on a live target merely to make a test convenient.

Keep secrets out of committed collections, screenshots, URLs, issue descriptions, and third-party analysis services. Use controlled local variables or a vault, redact evidence copies, and preserve the authentic request/response record under the approved access controls. A changed token, role, tenant, or target version can change the meaning of every later result: label each run accordingly.

## Build the surface and coverage map

1. Import approved specifications and collect observed operations from legitimate application use. Inventory method, path or operation name, version, caller role, object type, state effect, and sensitivity.
2. Compare documented, observed, and discovered operations. Only enumerate additional versions or endpoints within the authorization boundary and rate budget. Mark unknown ownership or third-party paths for clarification, not exploration by default.
3. Draw a small identity/action matrix. For each meaningful resource, identify the owner, another user in the same tenant, a user in another tenant (if authorized), a lower-privilege role, an administrator, and an unauthenticated caller where relevant. One role or tenant pair is not universal proof.
4. Trace complete business flows rather than isolated endpoints: creation, read, modification, export, deletion, approval, and post-action state. Note where a browser or mobile client filters information that the API itself still returns.
5. Record what was not reachable or not tested. Coverage is a statement of observed work, not a claim that every endpoint is safe.

### Make the inventory usable

A list of URLs is not yet a test plan. For each selected operation, carry one row that another tester can execute and a reviewer can challenge:

| Field | Record the decision, not a default |
|---|---|
| Operation and state | Protocol, method/message type, version, environment/build, expected side effect, and backing dependency if known |
| Caller and object | Issued identity, role/tenant, object owner or policy context, and safe fixture or test data |
| Expected rule | Who may read, change, invoke, or subscribe under which conditions; name the policy source or owner's confirmation |
| Comparison | Positive control, one bounded negative or boundary case, and the variable held constant between them |
| Authority and safety | Exact in-scope action, rate/state/data ceiling, contact/stop path, and any conditional approval |
| Evidence and result | Authentic request/response or event, time, target state, alternative explanations, reviewer disposition, and coverage outcome |

The matrix should include **in-scope but untested** operations and why. A version, tenant, role, function, or business flow not tested is not covered by implication. Discovery of a nearby host or service creates a scoping question, not new permission.

### Run a decision card

1. **State the security property.** Obtain an expected policy or owner-confirmed rule; a guess about how an API ought to behave is a hypothesis.
2. **Choose a safe contrast.** Use controlled identities and objects, one meaningful variable at a time. For state changes, use disposable fixtures and an agreed restore path; if there is none, design a non-mutating proof or stop at an observation.
3. **Prove the test position.** Confirm the expected identity, operation, target build, fixture, and evidence capture with a benign positive control.
4. **Exercise only the approved branch.** Keep the request count, payload size, concurrency, and effects within the RoE. An unexpected response is not authority to enumerate further or follow a credential into another system.
5. **Challenge the interpretation.** Check cache, session switching, shared objects, stale fixture, gateway behavior, and response-body meaning. Use a second perspective where the claim requires it; record what was not resolved.
6. **Decide and hand off.** Mark demonstrated, conditional, inconclusive, not observed under tested conditions, or untested. A finding requires evidence sufficient for its exact claim and review under the report route. Preserve the protected original and make a redacted derivative for the recipient.

This card is reusable across the classes below; it does not prescribe a tool or a count of requests.

## Test by security decision, not tool output

| Decision to test | Representative safe comparison | What would make it meaningful |
|---|---|---|
| Object authorization (API1) | Use two approved test identities and objects they own. Replay the same permitted operation with a changed object reference while holding the caller identity fixed. | Compare response and downstream state against the expected policy. A `200`, matching body, or changed object alone needs context: public objects, aliases, caches, and shared access may be legitimate. |
| Authentication (API2) | Compare an approved protected operation with no token, a valid token, and a controlled invalid/expired token. Trace login, refresh, logout, and alternative login routes in scope. | The service accepts a caller or token it should reject, under an observed state and policy. Decoding a JWT is not itself a flaw. |
| Object properties (API3) | Compare fields returned and accepted for two roles; add one controlled, non-destructive property to an update request if permitted. | The server exposes or accepts a property beyond the caller's authorized view or change rights; confirm the persisted state and impact. |
| Resource bounds (API4) | Within agreed low-impact limits, compare pagination, upload, query complexity, or per-caller throttling at small increments. | A limit is absent or bypassed in a way that creates plausible cost, availability, or abuse impact. Do not run a denial-of-service experiment without specific approval. |
| Function authorization (API5) | Attempt an administrative or state-changing operation with an approved lower-privilege identity and benign test object. | The function executes despite a policy that forbids that identity. Distinguish this from object ownership failure. |
| Sensitive business flow (API6) | Model a transaction limit or approval step with synthetic accounts and bounded repetitions. | The server permits a business outcome the owner says should be constrained; rate or CAPTCHA observations alone do not establish the rule. |
| Server-side fetch (API7) | If URL-accepting operations are in scope, use an approved callback endpoint or synthetic target. | Show the server made an unexpected request or crossed a trust boundary. Do not probe internal/cloud metadata addresses without a separate, explicit authorization and safety plan. |
| Configuration (API8) | Check transport, headers, CORS, errors, default/admin surfaces, and content-type behavior against the API's actual use. | A configuration enables a concrete exposure or bypass. A header missing from a JSON-only response is not automatically a finding. |
| Inventory (API9) | Compare documented and reachable versions and operations within scope. | An unmanaged or deprecated surface remains exposed with an actual control gap; undocumented does not automatically mean vulnerable. |
| Upstream consumption (API10) | Trace permitted calls to external services and how their responses influence local decisions. | A lower-trust response is accepted in a way that changes a security or business outcome. |

These are the official 2023 risk categories, not an exhaustive test list. OAuth/device-flow, JWT, race, GraphQL, SSE, software-supply-chain, cost-amplification, cache, and gRPC concerns may also be relevant. Evaluate each by its actual protocol and scope, with current references and separate safety limits; do not present them as additional OWASP Top 10 categories.

### Distinguish closely related decisions

**Object, function, and property authorization are different questions.** An object test asks whether `alpha` can act on `beta`'s object; a function test asks whether a caller can invoke an operation reserved for another role; a property test asks which fields a permitted caller may see or set. One endpoint may need all three comparisons. For a mutation, observe the persisted or downstream state when authorized and safe; accepting an HTTP request is not the same as applying an unauthorized change.

**Authentication tests need a state model.** Record how a credential is obtained, refreshed, expires, is revoked, and is bound to an audience or service. Compare a protected operation under controlled valid, missing, expired, and wrong-audience contexts only where approved. A decodable JWT is normal; a signature or claim-validation failure requires observed acceptance. For OAuth/OIDC, evaluate the actual client type and flow against the current protocol specification—for example [RFC 9700](https://www.rfc-editor.org/rfc/rfc9700/)—rather than declaring a finding from the presence of a grant name alone. Never paste a live token into a public decoder or shared evidence.

**Resource limits and sensitive business flows are not the same test.** A pagination or query-complexity bound protects compute, cost, and availability; a purchase, invitation, approval, or account-creation bound protects a business rule. Ask the owner for the expected limit and acceptable proof volume. A missing `429` does not establish that no effective limit exists, and a large-scale stress test is not implied by this method. Use low-impact increments and a separate authorization for any load, fraud, or account-abuse experiment.

**An upstream dependency is a trust boundary, not a free second target.** Map which API response, webhook, import, or URL-fetch result crosses into a local decision. Establish the control with an approved synthetic endpoint or fixture where possible. Internal-address probing, cloud metadata, third-party targets, credential use, and cross-service follow-on require their own explicit authorization and safety plan. A plausible attack chain belongs in an impact hypothesis until each link is observed or otherwise established.

### Protocol-specific branches

- **GraphQL:** inventory queries, mutations, fields, edges, and authorization at both node and resolver level. Ask whether batching, depth, and complexity change resource use, but stay within the approved load budget. Schema introspection can expand the test surface; its presence alone should not be reported without context and an agreed control expectation. See the [OWASP GraphQL Cheat Sheet](https://cheatsheetseries.owasp.org/cheatsheets/GraphQL_Cheat_Sheet.html).
- **WebSocket and SSE:** record who may establish a connection, subscribe, publish, and receive each message or event. Test authorization at the message/event boundary and after role change, logout, reconnect, and expiry where supported. Treat data in a stream as evidence, not an invitation to exceed the authorized subscriber scope.
- **SOAP:** inspect WSDL-defined operations, WS-Security or federation context, XML parsing limits, and authorization per operation. Avoid high-amplification parser tests unless separately approved.
- **gRPC:** use the supplied `.proto` definitions or authorized reflection to map services and methods. Compare identity and message-level authorization; do not assume an HTTP proxy understands Protobuf or HTTP/2 semantics without an observed request/response check.

For **WebSocket**, distinguish the opening handshake from each message: who may connect, send an action, receive a topic, retain a session after logout or role change, and reconnect. For **SSE**, the client subscribes to a server-to-client event stream; ask who may subscribe and receive each event and what happens after authentication or permission changes. Neither a successful connection nor an `Origin` header alone establishes a vulnerability. If a browser is the consumer, test browser-side effects under the approved web method as well.

**Unlike design check (synthetic GraphQL):** A query exposes `project { id, owner, billingContact }`. The owner says project members may see `id` and `owner`, while only billing-role members may see `billingContact`. In one approved build and two issued roles, first verify the billing-role response, then ask for the same field under the ordinary member role while holding project and query constant. Capture the authenticated role, field-level response, any error, and the policy source. If the field is returned, challenge whether the account inherited billing access or the value is public before accepting a property-authorization finding. If the GraphQL client masks the field but the raw response contains it, keep both observations. This tests one resolver and one state; it says nothing about every type or mutation.

### Cross-cutting branches beyond the Top 10

Select these by the actual architecture, not as mandatory payload sweeps:

| Branch | Meaningful test design | Boundary and evidence |
|---|---|---|
| Input to a parser, query, file, or template | Trace which parameter reaches which interpreter; use a benign differential or approved canary that can distinguish data from execution | Do not run high-amplification parser, command, database, or file-system probes without explicit limits. A syntax error alone is a candidate, not proof. |
| Upload, import, and export | Map accepted type and size, storage and rendering path, and any generated CSV/PDF/HTML consumer | A formula-like CSV cell or returned HTML matters only with an actual consuming context and impact; use synthetic data and an approved viewing workflow. |
| Browser credentials, CORS, and CSRF | Identify cookies versus explicitly supplied headers and the browser action needed; test whether an untrusted origin can read a protected response or cause a state change | Header reflection or `OPTIONS 200` alone is not a finding. A browser normally does not send a script-managed bearer header to an unrelated origin merely because `credentials` is enabled. |
| Cache and intermediary behavior | Compare caller-specific responses, cache keys, and origin/gateway interpretations with approved test accounts | Demonstrate a cross-user or cross-state effect before claiming leakage; do not infer one from cache configuration alone. |
| Version and dependency inventory | Compare documented and observed operations, gateway routes, older versions, and downstream calls within scope | An undocumented route is a coverage and ownership question until a control gap is shown. Package supply-chain assurance is an adjacent software-build review, not an automatic API pentest step. |
| Secret and token exposure | Inspect approved client bundles, responses, logs, and records for credential values or overbroad scope | Treat discovered live secrets as sensitive; preserve minimum evidence, rotate or revoke through the owner, and do not use them beyond the approved test. |

The reasoning and evidence requirements here are not a universal instruction to run every payload or tool. An adopter can attach versioned, locally authorized procedures where more depth is needed.

## From a primitive to a bounded impact story

A useful finding says more than “the endpoint returned 200,” but it must not promote a possible chain into an observed one. Separate three layers in notes and report:

| Layer | Example for an object-authorization result | Claim ceiling |
|---|---|---|
| **Observed** | One approved caller retrieved one unshared synthetic record belonging to another test identity on a named build | The exact operation, identities, object class, and environment shown by evidence |
| **Inferred, with basis** | The server likely omitted or misapplied an ownership decision on that read path | State competing explanations and what review ruled out |
| **Possible, not tested** | Other records, tenants, versions, or downstream workflows might share the defect | A hypothesis for owner triage or separately authorized scope, not a confirmed blast radius or severity multiplier |

The same distinction applies to function-level access, server-side fetch, token validation, business-flow limits, and multi-step paths. Draw a chain only when each observed link and each untested link is labeled. A primitive may warrant prompt notice without proving the entire chain. Severity and remediation priority use the adopter's scoring model, actual data and exposure context, and evidence—not a fixed category-to-Critical mapping. An adjacent system becoming *relevant* to impact analysis does **not** make it in scope for testing.

## One bounded API example: object ownership

**Synthetic target:** `GET /api/v1/projects/{projectId}` returns a project record. Two approved test users, Ada and Ben, each own one synthetic project. The engagement permits read-only cross-user authorization checks on those two objects.

| Step | Record |
|---|---|
| Baseline | Ada requests her project and receives the expected project. Ben requests his and receives his. Record identity, project IDs, time, environment, and response fingerprint. |
| Comparison | Holding Ben's valid session fixed, request Ada's project ID once. Do not enumerate IDs or access real customer data. |
| Alternative explanations | Could the project be deliberately shared? Is the response a cache artifact? Did the client silently switch identities? Does the body actually contain Ada's protected fields? |
| Decision | If the ownership policy forbids Ben's access and a fresh, reproducible response exposes Ada's record, document an object-authorization finding. If policy or target state is unresolved, mark the result inconclusive and name the missing evidence. |
| Report handoff | Provide redacted requests/responses, expected-versus-observed behavior, affected operation and identity relation, reproduction preconditions, impact, scope limits, and a retest condition. |

This example is deliberately read-only and synthetic. A real engagement may need a different ownership model or a different safe proof. The tester owns the decision, and a qualified reviewer can challenge it from the recorded conditions.

## Evidence, review, and reporting

For every candidate, preserve the exact operation and version, caller identity/role/tenant, relevant object ownership, target state, time, request and response or equivalent event, expected behavior, observed behavior, safety limit, and possible alternative explanation. A screenshot can orient a reader; it is not a substitute for reproducible conditions. Redact secrets and personal data in outward copies while preserving controlled originals according to the engagement's retention rules.

The reviewer should be able to ask: Was the action authorized? Is the comparison like-for-like? Is the unexpected result repeatable? What else explains it? What did the tester not attempt? Only then decide whether to report a confirmed finding, a conditional observation, a testing limitation, or no finding. Severity is a separate, context-bearing judgment; do not assign a fixed severity from an OWASP category alone. A remediation suggestion should address the failed decision boundary, not merely name a product or return code.

When a result is reported, include a retest condition: which identity/action/object relation must now be denied or bounded, under what target state, and what evidence will demonstrate the change. Retesting one operation does not prove every related implementation is fixed; document the verified scope.

## Automation boundary and change control

A script or agent can help build an inventory, replay approved comparisons, classify candidate responses, and assemble evidence. It cannot infer authority from reachability or turn a plausible response into a finding. Any future AI-enabled extension needs explicit tool/data/action permissions, rate and state-change controls, observable logs, human review points, and a way to stop and recover. The human-led method above remains usable without that extension.

If an adopter automates a test card, bind the **exact approved scope and current authorization version** to the run; do not pass a broad target string and let a planner expand it. The run record should distinguish *proposed* operations from *executed* operations, record caller identity references without secret values, target build, rate and state-effect budgets, request/response evidence pointers, and the stop or escalation decision. A candidate response remains candidate until a qualified person checks policy, alternatives, and the protected original. Discovery of a new host, identity, object class, or chain step returns to scope review; it is never an automatic continuation. A script that reproduces a result is valuable, but it does not make that result a finding by itself.

Maintain this guide as a versioned method. At each review, check OWASP edition and linked protocol guidance, tool-neutral setup validity, new API patterns, safe proof examples, source coverage, and reader feedback. A source or tool update may require a method change; a new tool name alone does not.
